# Mountpoint for Amazon S3 と S3 Access Points の使い分け

🌐 **言語**: **日本語** | [English](mountpoint-vs-s3-access-points.en.md)

> **区分**: 表の内容は、2026-11-24 に読んだ公式文書の記載です。出典 ID は [ツールの事実確認](tool-facts.md) の出典一覧にあります。FSx for ONTAP のアクセスポイントに Mountpoint for Amazon S3 を向けた実機の確認は、まだありません。`C` は文書に記載がなく未実測の項目です。

FSx for ONTAP のデータに届く経路は、次の 3 つがあります。このページは、3 つの経路の制約を同じ軸で並べ、選ぶ手がかりを示します。どの経路にも向く場面と向かない場面があり、順位は付けません。

## 比べる 3 つの経路

| 記号 | 経路 | 入口 | FSx for ONTAP での前提 |
|---|---|---|---|
| a | Mountpoint for Amazon S3 でアクセスポイントをマウントする | `mount-s3 <エイリアス> <マウント先>` | Mountpoint が FSx for ONTAP のアクセスポイントを受け付けるか、文書に記載なし（`C`）。Mountpoint の README は Amazon S3 以外の S3 互換ストレージをサポートしないと書く（S16） |
| b | S3 API を直接使うツール（AWS CLI、s5cmd、rclone）でアクセスポイントに届く | `aws s3 ...`、`s5cmd ...`、`rclone ...` | ARN またはエイリアスを指定できる。指定できるかは、AWS CLI は文書にあり（S6）、s5cmd と rclone は記載なし（`C`） |
| c | FSx for ONTAP のボリュームを NFS または SMB で直接マウントする（参考） | OS の `mount` | アクセスポイントを付けても、NFS と SMB での動作は変わらない（S4） |

## 軸ごとの制約

| 軸 | a: Mountpoint | b: S3 API のツール | c: NFS または SMB（参考） | 出典 |
|---|---|---|---|---|
| ファイル名の変更 | S3 の汎用バケットでは、リネームを模倣しない。リネームは S3 Express One Zone だけが対象 | FSx for ONTAP のアクセスポイントの対応表に、リネームに当たる操作はない（部分的な一覧）。Transfer Family の文書は、リネームと追記が使えないと書く | ファイルシステムの操作として実行できる（`C`: このページでは出典を取っていない） | S14、S17 |
| 追記 | S3 Express One Zone だけが対象。`--incremental-upload` が要る | `PutObject` は全体を書き直す形（S3 API の一般仕様、`C`） | ファイルシステムの操作として実行できる（`C`） | S14、S17 |
| 上書き | 既定では新規ファイルの作成だけ。上書きは `--allow-overwrite` と切り詰めての書き込みが要る | `PutObject` で同じキーに書ける。条件付き書き込みは未対応 | ファイルシステムの操作として実行できる（`C`） | S1、S14 |
| ディレクトリ | キーの `/` から推定する。`mkdir` はローカルだけの操作。既存のディレクトリは削除もリネームもできない | キーのプレフィックスとして一覧する。ボリューム内の実ディレクトリとの対応は `C` | 実ディレクトリを作成、削除できる（`C`） | S14 |
| メタデータ | 所有者や権限の変更を模倣しない。更新日時とサイズは限定的で、変更できない | オブジェクトのメタデータ。ファイルの UNIX 所有者や権限が S3 のメタデータとして見えるかは `C` | ファイルの所有者、権限、ACL を持つ | S4、S14 |
| 権限の判定場所 | プロセスの IAM 認証情報で S3 側が判定し、その後に、アクセスポイントに設定したファイルシステムユーザーの権限で判定する。ローカルでは、既定でマウントしたユーザーだけが読める（`--allow-other` で広げる） | IAM とアクセスポイントのポリシーで判定し、その後にファイルシステムユーザーの権限で判定する | クライアントの ID を、ボリュームのセキュリティスタイル（UNIX のモードビットか NFSv4 ACL、NTFS の ACL）で判定する | S4、S14 |
| ネットワーク経路 | S3 のエンドポイントへ HTTPS。VPC 起点のアクセスポイントなら、同じ VPC の VPC エンドポイントを通す。インターフェイスエンドポイントを使うときは `--endpoint-url` が要る | 同じ。ツールによって `--endpoint-url` の扱いが違う（s5cmd はパススタイルに戻る） | SVM のエンドポイントへ、ファイルプロトコルで直接（`C`: このページでは出典を取っていない） | S3、S9、S13 |
| キャッシュ | メタデータとデータの任意のキャッシュがある。有効にすると、メタデータの有効期間は既定で 1 分。他のクライアントが変更したオブジェクトは、最大で既定 1 秒間、古いメタデータが見える | ツール側のキャッシュは持たない（`C`） | NFS と SMB のクライアントのキャッシュに従う（`C`） | S14 |
| 向く用途 | 大きなオブジェクトを高いスループットで読むアプリケーション。新規ファイルを 1 つのクライアントから順に書く用途 | 一括コピー、同期、バッチ。サーバー側コピー（[サーバー側コピー](server-side-copy.md)） | POSIX の操作（リネーム、追記、権限変更）を要するアプリケーション | S14 |

## 選び方

| 条件 | 先に検討する経路 | 確認が要ること |
|---|---|---|
| アプリケーションはファイルのパスしか受け付けず、読み出しが中心 | a または c | a は、Mountpoint が FSx for ONTAP のアクセスポイントを受け付けるかを実機で確認する。c は、クライアントの ID と ACL の設計 |
| 一括コピー、定期同期、バッチの取り込み | b | ツールがアクセスポイントのエイリアスを受け付けるか、対応表が未対応とする操作を発行しないか |
| リネーム、追記、権限変更を使うアプリケーション | c | S3 API 側から同じデータをどう使うか |
| S3 側の権限を IAM とアクセスポイントで絞りたい | a または b | アクセスポイントのファイルシステムユーザーの権限が、実際の上限になる点 |
| 別アカウントのバケットとの間でデータを移す | b | 同一リージョンのコピーだけ。[サーバー側コピー](server-side-copy.md) |

## 2026-11-24 の実機確認の結果

経路 a と経路 b は 2026-11-24 に 1 回ずつ実機で確かめました（[2026-11-24 の記録](../benchmarks/records/2026-11-24-client-tools-stage3.md)）。Mountpoint for Amazon S3 は、FSx for ONTAP のアクセスポイントをエイリアスでも ARN でもマウントできました。新規書き込み、読み出し、上書きと削除（フラグ付き）、リネーム、追記の結果は、同じ回の通常のバケットのマウントと同じでした。経路 c（NFS）は確かめていません。
